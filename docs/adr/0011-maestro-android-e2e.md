# 0011. Maestro for Android E2E, run locally, no CI for now

- **Status:** Accepted. Implemented on 2026-11-20: four flows in
  [`.maestro/`](../../.maestro/README.md), run as described in
  [docs/e2e-emulator.md](../e2e-emulator.md).
- **Date:** 2026-11-19

## Context

The E2E gate runs in a browser ([0006](0006-web-export-as-e2e-harness.md)),
so the flows that matter most on a phone are not automated: the `.zip`
export and restore, the system file picker and the share sheet
([docs/TESTING.md](../TESTING.md#known-gaps)). The
backup flows need `react-native-zip-archive`, a native module that does
not exist in Expo Go, so they can only be tested on a dev or release
build ([0004](0004-zip-backup-of-record.md)).

The backup flow was already checked once on an emulator with adb scripts:
coordinate taps, screenshots, `dumpsys` and `logcat` greps. It worked, but
a tap meant for "Restore" landed on "Export"
([docs/e2e-emulator.md](../e2e-emulator.md)).

## Decision

- **Runner:** [Maestro](https://maestro.mobile.dev). Flows are YAML,
  select elements by visible text, `accessibilityLabel` or `testID`, and
  wait for the UI on their own. It drives the installed app from outside,
  so the app needs no test code beyond a few `testID`s. The UI kit
  already requires `accessibilityLabel` on icon buttons, which gives most
  selectors for free.
- **Target:** a dev or release build installed on a local Android
  emulator. Never Expo Go, because of the native zip module.
- **No CI for now.** Flows run locally, by hand.

## Alternatives considered

- **Detox.** A gray-box framework: it needs an instrumented test build
  of the app next to the normal one, so it changes the Android build
  (through a config plugin here, since `android/` is generated by
  `expo prebuild` and git-ignored), and that native setup has to follow
  every React Native upgrade. Maestro can drive a release APK exactly as
  it ships.
- **Appium.** A WebDriver server plus a client library and drivers: the
  most general option and the most infrastructure, for an app with one
  platform and a handful of flows.
- **The adb smoke scripts already in
  [docs/e2e-emulator.md](../e2e-emulator.md).** Good for a one-off check,
  but they tap by pixel, have no assertions and break with any layout
  change. They are a debugging aid, not a regression test.

## Why no CI yet

Running this in GitHub Actions means building the APK in the job (a
prebuild and a Gradle release build) and booting an Android emulator on
the runner, on every run. That is heavy and slow next to the rest of the
pipeline, and an emulator boot adds failures that have nothing to do with
the app. The
suite is small and local runs are enough to see whether it is worth the
cost. CI can be added later, for example as a separate, non-required workflow
like mutation testing ([0010](0010-mutation-testing-stryker.md)), and that
would be a new ADR.

## Consequences

- Android E2E protects only what someone runs. A regression in a native
  flow can still reach a release unless the suite is run before it.
- Each run needs a fresh build of the app under test and an emulator with
  the test files on it (the demo backup archive for restore).
- Selectors by `testID` survive copy and translation changes; selectors by
  text break when the English strings change. Elements picked by position
  should get a `testID`.
